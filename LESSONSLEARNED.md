# LESSONSLEARNED.md

Tracked durable lessons for `intake`.
Unlike `CHATHISTORY.md`, this file should keep only reusable lessons that should change how future sessions work in this repo.

## How To Use

- Read this file after `AGENTS.md` and before `CHATHISTORY.md` when resuming work.
- Add lessons that generalize beyond a single session.
- Keep entries concise and action-oriented.
- Do not use this file for transient status updates or full session logs.

## Lessons

- Document the repository around its real execution, curation, or integration flow instead of only the top-level folder list.
- Keep local-only, private, reference-only, or generated boundaries explicit so published or runtime behavior is not confused with offline material or non-committable inputs.
- Re-run repo-appropriate validation after changing generated artifacts, diagrams, workflows, or other CI-facing files so formatting and compatibility issues are caught before push.
- Receipt PDFs from snowbridge may be image-only scans (no text layer); always attempt pdfplumber extraction first and fall back to pytesseract rather than assuming one approach works for all files.
- When inbox processing stops unexpectedly, check `systemctl --user status intake-daemon` first; an `inactive` service with `status=200/CHDIR` means systemd could not enter the configured working directory, so the daemon never reached its own volume-availability checks.
- For editable installs launched by systemd, resolve repo-local config and output paths from `intake/cli.py` instead of caller cwd, and keep the unit `WorkingDirectory` on a stable path like `%h` rather than a mount-dependent repo path.
- Outbound receipt notifications should be best-effort: wire them into every successful ingest path, but never let a Signal or relay failure block the receipt move, sidecar write, or DB upsert.
- For expensive downstream consumers like `personal-finance`, emit a stable batch JSON and trigger once per successful intake batch (`process`/`backfill`/daemon cycle) instead of spawning one heavyweight downstream run per receipt.
- When both inbound Gmail polling and outbound Gmail notifications are enabled, reuse the same `shock-relay` gmail-imap config by default and keep the notification-specific recipient/subject settings in a separate `[gmail]` section rather than overloading `[email]`.
- For scheduled report generation, use a separate oneshot systemd service plus timer rather than embedding report writes in the long-running intake daemon loop; that keeps scheduling explicit and lets the report be run on demand through the same service unit.
- Route tracked systemd unit generation through `./util-repos/clockwork` instead of expanding more inline service/timer strings in `intake/cli.py`; keep the public `intake ... --install` commands stable, but let `clockwork` own the scheduler artifact shape.
- Keep generated reports self-contained: prefer inline SVG/CSS charts in HTML and simple text-bar fallbacks in Markdown so scheduled report artifacts stay portable and do not depend on external JS, CDNs, or browser-only runtime data fetching.
- For merchant cleanup, exact keyword hints across the full OCR text recover real retailers more reliably than fuzzy matching only the first merchant line; use the full receipt text to catch later hints like `KROGER PLUS` or `Walmart.com`.
- For intake reports that are meant to be browsed from the served site, link folders and receipts through the Snowbridge File Browser (`https://files.snowbridge.internal/files/...`) instead of local `file:///...` paths so the links work remotely and from the report UI itself.
- Total extraction should be line-aware rather than regex-last-match: exclude non-payment totals like loyalty points/items/tax/discount lines, and when no grand total is printed, compute the payable amount from subtotal plus taxes/fees minus discounts.
- Purchaser extraction should require stronger label boundaries for generic words like `customer` or `name`; otherwise OCR phrases such as `customer satisfaction` can be mis-stored as cardholder names.
- Category keyword matching should be token/phrase-aware rather than raw substring matching; otherwise short fuel keywords like `mobil` will falsely classify telecom receipts whose text contains `mobile`.
- Telecom merchants often print the legal entity rather than the customer-facing brand; add explicit canonical merchant patterns like `vodafone` so report rollups do not split between brand and legal-company variants.
- In report recent tables, category links should be derived from the normalized category path, not the receipt file path; synthetic/email rows do not have local PDFs, but their category folders can still be linked under the receipt root.
- Only emit report file/folder links when the local target can be resolved under the mounted receipt tree; otherwise show plain text so stale DB paths do not create dead links in the report UI.
- Kroger OCR can degrade into variants like `POGER PLUS` or `kreager.com`; merchant recovery should include known-pattern hints for these later-line variants instead of trusting the first OCR line.
- Gmail-rendered receipt PDFs often put browser chrome or message headers on the first line; merchant recovery should prefer later sender/domain/store signals like `orders@em.autozone.com` over the opening `Gmail - ...` text.
- Payment-card footer text like `Cardholder Signature Verified` or `Customer Copy` should be blacklisted from purchaser extraction, or OCR cleanup will reintroduce false purchaser names during merchant-correction sweeps.
- Bass Pro receipts can OCR down to `World` while still containing later `basspro.com` signals; add domain-aware merchant patterns for these print-receipt cases instead of relying on the first merchant line.
- Canonicalization-only merchant sweeps must not blindly overwrite previously AI-derived totals or card metadata with weaker Tesseract output; when only the merchant casing/normalization is changing, preserve higher-fidelity numeric fields unless a fresh extraction actually improves them.
- Recent-report navigation should not trust `receipt_dir` blindly: when a stored PDF path is stale, fall back to a unique on-disk filename match, and when an email/synthetic receipt has no local file, link its row through to the best available category folder instead of leaving a dead or missing target.
- Merchant consolidation belongs in a config-driven alias map (`[merchants]` in `categories.toml`) rather than only hardcoded regex patterns; canonical entries with empty alias lists handle case/punctuation normalization, while explicit alias lists handle clean-text name variants (e.g. "O'Reilly Auto Parts" → "o'reilly").
- A post-ingestion `consolidate` command that patches the DB and sidecars in-place (no re-OCR) is more practical than re-running backfill; it should sweep both DB-tracked rows and all `.intake.json` files on disk to catch orphaned sidecars.
- Sidecar-only backfill upserts must guard against filename collisions: if the filename already maps to a different `receipt_dir` in the DB, skip rather than overwrite the existing row silently.
- Duplicate receipt detection (same merchant + total within a day window) is best expressed as a separate `dedup` command with `--remove`; auto-selecting the keeper by model rank then field completeness (purchaser/card_last4) then processed_at avoids interactive prompts while still being deterministic.
- When `dedup --remove` drops a row that held unique purchaser data, that field is lost; consider a merge-fields-into-keeper step before deletion, or at minimum surface the discarded fields in the output so the user can manually patch the keeper row.
- "Balance Due: $0.00" on a fully-paid invoice is not the transaction amount; total extraction must prioritise invoice/order/amount-due labels over balance/balance-due labels, trying the more specific group first and only falling back to balance-due when nothing positive is found.
- dedup --merge is safer than --remove: before deleting duplicates, promote any purchaser/card_last4 fields from non-keepers into the keeper row so no cardholder metadata is silently lost.
- For sites published behind `wiring-harness`, keep the localhost backend and its user-level systemd unit in the service repo, and treat `wiring-harness/services.toml` as the only place that should know the external HTTPS hostname and Caddy proxy target.
- Merchant cleanup must run after both OCR parsing and any later AI/email extraction merge; otherwise mixed-case aliases and blacklisted header text can leak back into stored receipts even when the initial parse path is normalized.
- Category selection should prefer the most specific matching keyword phrase across merchant and OCR text, not just the first rule in config order; otherwise phrases like `kroger fuel` get swallowed by broader matches like `kroger`.
- Some POS receipts print both an intermediate `BALANCE` and the final tender line; total extraction should prefer explicit payment-card/tender amounts (`mastercard`, `visa`, `debit`, etc.) over generic balance fallbacks so the charged amount wins.
- Manual receipt fixes are too valuable to leave in ad hoc `sqlite3` edits or chat logs; route corrections through a durable audit trail with field-level before/after diffs so they can be mined later for auto-healing rules and regression fixtures.
- Receipt filenames should stay structurally canonical even under collisions or partial metadata: use `YYYYMMDD_HHMM.EXT`, borrow the minute from the source file or mtime when OCR lacks one, and advance minute-by-minute instead of appending `-1` / `-2` suffixes that break downstream assumptions.
- Filename date policy needs a strong date parser to work safely: once month-name dates like `March 22, 2026` are parsed, purchase-date filenames become possible, but bulk historical renames should still be curated because some OCR-derived dates are wrong enough to move files to the wrong year/day.
- Duplicate cleanup should move through a first-class audited path: `intake dedup --remove` should exhaust the artifact, keep the sidecar in sync, and record the keeper/path change before deleting the duplicate DB row.
- Merchant/amount/date heuristics are only a fallback for duplicate detection; PDF-based ingest should persist a SHA-256 `file_hash`, short-circuit exact hash collisions at intake time, and let `dedup` prefer exact hash matches over fuzzy duplicate guesses.
- Schema changes for existing SQLite tables cannot rely on `CREATE TABLE IF NOT EXISTS ... new_column ...` alone; if startup also creates indexes on that new column, keep the index creation in a post-migration step or older live databases will fail before `ALTER TABLE` runs.
- Payment-brand labels like `App Name: Discover` are not purchaser names; anchor OCR purchaser extraction to the start of a label line and blacklist card brands, while allowing card-last4 recovery from nearby standalone 4-digit tokens after `VISA` / `DISCOVER` / similar tender lines.
- When a receipt exposes `card_last4` but not a purchaser, backfill the purchaser from the most recent non-empty purchaser already seen for that same card; this keeps later receipts usable even when the current OCR missed the cardholder name.
- Purchaser cleanup needs a shared normalizer, not separate OCR/AI/DB heuristics: canonicalize known aliases (including email forms), lowercase/reorder name variants centrally, and blacklist footer/repair-note phrases before both persistence and audited correction sweeps.
- Cashier/counter staff lines can fool AI into emitting a short first name as the purchaser; reject purchaser candidates that fuzzily match names found on `cashier` / `counter` / similar staff-labeled lines so card-history backfill can win instead of preserving the cashier.
- Parking citations and similar notice/receipt hybrids need explicit paid-vs-unpaid handling: if the text says `Status: Unpaid` and `Total Amount Paid` is zero, do not treat `Amount Due` as spend; if `Total Amount Paid` is present and positive, prefer it over a later zero `Amount Due`.
- Keeping only `receipts.raw_text` in SQLite is not enough for debugging extraction regressions; future receipt processing should persist sidecar-adjacent `*.ocr.txt` and `*.ai.json` artifacts and move them along with the PDF so investigation does not depend on DB access or discarded AI responses.
- Missing-card sweeps are low-yield without a live AI key: parser recovery from stored OCR can pick off a few rows, but OCR-only re-extraction often finds nothing new, so deeper backfill campaigns should be run when OpenAI extraction is configured.
- TOML table scoping is easy to misread in local `settings.toml`: keys placed after a header like `[web]` belong to that table, so keep intake-wide settings above the first table or hoist known misplaced keys during settings load to avoid silently disabling features like auto-pass OpenAI resolution.
- Keep the auto-pass wiring single-sourced in `config/settings.toml`; a second repo-local config file for the same `auto_pass_profile` / `openai_api_key_entry` settings just creates ambiguity and makes breakage harder to diagnose.
- SaaS invoices and credit notes often expose the real purchaser only inside a `Bill to` block; purchaser extraction should scan that block for known email aliases instead of relying only on `Cardholder:`-style labels.
- OCR often corrupts masked card-number lines on the final digit group (`S653` for `5653`, `O123` for `0123`); when a line is explicitly labeled `Card Number`, treat the final 4-character token as a candidate last4 and apply conservative OCR digit fixups before giving up.
- Itemization needs a tri-state store, not just a list: keep `items_json = NULL` for “not yet attempted”, `items_json = []` for “attempted but no usable items”, and a non-empty JSON array for successful breakdowns; otherwise historical backfills cannot distinguish missing coverage from true no-item receipts.
- Historical itemization should be a first-class audited command (`intake itemize`) rather than a one-off script so DB rows, sidecars, report coverage, and downstream personal-finance all stay in sync when the corpus is backfilled.
- Merchant history is a separate analytical view from top-merchant totals: keep a `merchant_by_month` aggregate in the report query so the report can show both exact merchant-month tables and compact top-merchant trend cards without re-aggregating raw receipts in the template.
- Once the report grows beyond a single summary page, generate static directory/detail pages and link into them from the main report instead of endlessly expanding one long dashboard; this keeps `intake serve` simple while still allowing drill-down by merchant.
- Report pages are operational dashboards, not prose articles; avoid fixed narrow `max-width` containers and let tables/charts use the full browser viewport with only modest gutters.
- Report aggregates must distinguish `SUM(total)=0` from “no known totals at all”: keep a `known_total_count` alongside `SUM(total)` and render all-null spend buckets as `—`, or the report will incorrectly imply real zero-dollar spend for receipts whose totals were never extracted.
- Merchant/shop certifications should live as structured receipt metadata with evidence, not as ad hoc merchant-name suffixes, category hacks, or a separate side log; persist them through DB + sidecars + downstream JSON and surface them on merchant detail pages so future correction workflows stay audited and queryable.
- Historical certification enrichment should be a first-class audited command (`intake certify`) with a tri-state store (`NULL` = not attempted, `[]` = attempted/no claims, non-empty JSON = claims found); otherwise corpus-wide backfills fall back to one-off scripts and cannot distinguish missing coverage from a true “no certification found” result.
- `intake correct` retries must be able to resync sidecars from the current DB row even when there is no new DB diff; otherwise a partial failure that updates the DB before the sidecar write will leave mounted metadata stale forever.
- Review novelty flags should be gated behind basic plausibility checks: only mark `new_merchant`, `new_card_last4`, `new_merchant_card_pair`, or merchant spend outliers when the row already has a usable merchant and total, or the review queue fills with noisy first-seen junk instead of actionable novelty.
- The terminal `intake review` view should never truncate reason strings; full reason summaries are part of the operator signal and need to stay visible both in stdout and in `reports/review.md`.
- Absolute total guards are safest as review reasons, not parser rewrites: keep the parsed amount intact, but add explicit `total_over_250/500/750/1000` reasons so likely OCR decimal/comma mistakes surface without corrupting legitimate high-value receipts.
- High-total guards should also affect extraction tiering: when OpenAI is configured, totals above the guard should get a high-model pass before being persisted, while still preserving the original guard as a review signal.
- Itemized receipt adjustments can be negative; keep refund/discount lines from AI itemization instead of normalizing them away, or item-level reporting will no longer reconcile to the receipt total.
- Processed-receipt notifications should compute Snowbridge/File Browser links consistently for every outbound channel, and the live daemon must be restarted after notification-code changes or it may keep sending messages from stale imports.
- Gmail receipt notifications should include available sidecar-adjacent artifacts (`*.ocr.txt`, `*.intake.json`, `*.ai.json`) alongside the primary receipt link so reply follow-ups do not need to ask for OCR/JSON context again.
- Inline email receipts need a real artifact under the Snowbridge receipt tree before notifications are sent; DB-only synthetic rows cannot produce File Browser links.
- Handled receipt emails should archive the raw RFC822 message locally before being marked read or moved to the processed label; attachment PDFs and parsed inline bodies are not enough for later audit/debugging.
- Already-recorded receipt emails can still need Gmail filing; the fetcher should mark them read and move them to the configured processed label without reprocessing attachments or inline bodies.
- Process tests that exercise the receipt path should mock both pre-classification OCR and document-type classification when using fake media fixtures; otherwise CI environments without valid image/PDF/ffmpeg support will fail before the intended extraction mock is reached.
- Receipt-media support must stay centralized: if intake adds non-PDF formats like `.jpg` or `.mov`, keep the supported suffix list in one shared module and reuse it in inbox discovery, backfill, OCR/AI preview generation, and report link resolution, or the pipeline will process some formats while silently ignoring or mis-linking them elsewhere.
- Email subject expansion can create feedback loops: once Gmail ingestion starts searching broad payment/receipt subjects, it must explicitly skip intake-generated notification emails (for example `[intake] Receipt processed: ...`) or the mailbox processor will begin marking its own outbound alerts as fresh intake candidates.
- When Gmail receipt discovery expands beyond subject keywords into sender-based searches, only mark/move a message after intake actually saved an attachment or wrote an inline receipt row; otherwise a broad sender hint can silently drain unrelated mailbox traffic into the processed label.
- Issuer payment-confirmation emails need a dedicated extraction path instead of the generic merchant-receipt parser; card-account phrases like `VentureOne Credit Card...5653` and `Account ending in 7875` can otherwise be misread as merchant names or totals, and effective dates must prefer labeled posted dates over the earliest date in the message body.
- Scheduled/upcoming payment or purchase notices are not receipts: file them as ignored email records before attachment/AI processing, and provide a cleanup path for historical rows so forecasts do not inflate spending or look like duplicates.
- Posted card-payment confirmations can legitimately repeat merchant and amount across nearby dates; keep them out of merchant+total heuristic duplicate grouping and rely on message-id/exact-artifact checks for true email duplicates.
- Provider payment reminders can expose multiple plausible amounts in one email; for installment-based insurance notices like Progressive renewals, treat the minimum installment as the predicted payment and only fall back to pay-in-full or total-premium amounts when no installment amount is present.
- The systemd wrapper must pin `PYTHONPATH` to this repo checkout before `import intake.cli` and `python -m intake.cli`; otherwise a user service can silently import an older site-packages install, making live daemon behavior diverge from the checked-out code even when the unit itself restarts cleanly.
- Gmail IMAP labels like `[Gmail]/All Mail` and `[Gmail]/Sent Mail` need quoted mailbox names during `SELECT` / `EXAMINE`; when scanning reply traffic across Gmail labels, prefer `All Mail` first, treat the reply sweep as best-effort, and dedupe follow-up actions by the replied-to thread token (`In-Reply-To`) rather than by reply `Message-ID` alone because Gmail can surface multiple copies of the same conversation with different message ids.
- Intake notification replies must be excluded from the main inline-receipt email parser before AI extraction; quoted `Receipt processed` bodies contain merchant/total/category text and can otherwise be re-ingested as synthetic receipt rows instead of only becoming `receipt_updates` reply notes.
- Intake-generated notification emails should be filed into their own Gmail label before DB dedup and must never be reprocessed as receipt candidates; keep that label separate from the processed-receipt label so operational alerts stay easy to review.
- Intake-generated notification emails should be left untouched in INBOX for a grace period before filing; even label-only handling can race user-facing Gmail/device notifications, so apply labels only when filing.
- Intake-generated Gmail reply-link messages must also be treated as internal messages: honor `X-Portfolio-Service: intake` / `X-Crew-Chief-Intent: reply-link`, file them to the notification label, and never parse the generated `Snowbridge receipt link requested` body as a new user request.
- Treat merchant+total duplicate groups as review candidates, not automatic truth: repeated restaurant tabs or card payments can share amounts across nearby days, so use `intake dedup --hash-only` for conservative sweeps and curate heuristic groups before deleting rows.
- Staff/service metadata belongs in structured `staff_json` plus sidecars/reports/downstream events; use `intake staff` for historical OCR backfill instead of overloading purchaser names or free-form correction notes.
- Manual category corrections for inline email receipts must move or materialize the Snowbridge email text artifact and sync its sidecar; changing only the DB leaves reports with folder-only links.
- Avoid broad category keywords such as color words in cannabis rules; use explicit cannabis merchant/product terms and add known App Store/KeePass signals under software so full-text classification does not misfire.
- Itemized receipt summaries in report tables must be capped before rendering, not just wrapped with CSS; long product names otherwise force operational tables wider than the viewport.
- Inline email receipt sidecars must serialize structured fields such as items, certifications, and staff before JSON writes; a post-DB sidecar failure can leave the receipt row present while Gmail filing and `email_receipts` recording never happen.

### 2026-06-07 — Processed-receipt email bursts should use the shared Gmail digest

- When receipt processing can emit many Gmail notifications in a burst, enable `[gmail].digest = true` so processed-receipt notices are queued through shock-relay and sent as an aggregate.
- Keep reply-link follow-ups immediate; they are user-requested responses rather than routine operational alerts.

### 2026-06-08 — Japanese cash-tender labels are not transaction totals

- Japanese receipt parsing must distinguish purchase totals such as `合計` / `税込合計` from cash-tender labels such as `お預り` / `お預かり`; the tendered cash amount can be larger than the receipt total and should not override a valid total.
- Japanese-only merchant lines should not be discarded by ASCII-only merchant cleanup; otherwise the parser can fall through to amount lines and store numeric text as the merchant.
- A language/locale hint is useful for currency defaults, but if downstream review needs to know a receipt was Japanese, persist a language field instead of only using a transient parse hint.
- For non-English receipts, keep `raw_text` / `*.ocr.txt` as the original source artifact and store the English translation in a separate structured field such as `translated_text`; overwriting OCR text destroys the audit trail needed for later parser fixes.
- Default non-English translation to the shared local `crew-chief` Ollama service when available, and keep translation as secondary metadata only; merchant, total, and currency should still come from deterministic parsing plus explicit review/high-tier correction paths rather than from the translation text alone.
- Historical locale backfills on noisy phone photos should not blindly re-run the OCR parser and overwrite trusted merchant/total fields; OCR-only refreshes can get worse. For old low-quality receipts, use a vision-capable model or explicit visual review to fill `language` / `translated_text`, and only change merchant/total when the prior value is missing or the new evidence is clearly stronger.
- `currency = JPY` is a strong clue but not proof that a receipt is Japanese; false positives can come from OCR/currency heuristics on ordinary USD receipts. Before mass locale backfills, review outliers visually or with an image-capable model and correct the false positives back to `USD` / `en` instead of assuming the whole bucket is Japanese.
- Historical translation/locale cleanup should live behind a first-class CLI (`intake translate backfill`) rather than one-off scripts, and other repos that only need receipt/image OCR translation should prefer shelling out to `intake translate text|receipt --json` instead of building a separate receipt-specific translator.

### 2026-06-09 — Locale receipt terms need boundary-aware matching

- Receipt label matching should treat short locale terms such as `USt`, `TVA`, `TTC`, or `bar` as whole labels/words, not raw substrings; naive substring checks can misread unrelated English labels like `customer` as tax lines and silently corrupt computed totals.
- When adding new locale support, extend both locale detection and total/subtotal/tax exclusion vocabularies together; language detection alone is not enough if the parser still only understands English/Japanese amount labels.

### 2026-06-09 — Intake CI formatting must be checked with the workflow commands too

- `pre-commit run --all-files` is necessary but not sufficient for this repo's hosted CI; before pushing Python changes, also run the workflow-equivalent `ruff format --check .` and `black --check --diff .` because the separate GitHub Actions formatter job can still catch files that local hooks leave untouched.

### 2026-06-10 — Credit-reporting alerts need provider-specific intake paths

- Credit-reporting emails from providers like Equifax, Experian, and Capital One CreditWise are not receipts and usually do not match generic receipt/payment heuristics; they need explicit subject/sender candidate search terms plus a structured non-spend parser.
- For these alerts, store them as finance metadata (`finance/credit-reporting`) with `total = NULL` rather than forcing a faux spend amount or filing them as ignored mail.
